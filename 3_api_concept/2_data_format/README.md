## Response Section
### JSON (JavaScript Object Notation)
#### ข้อดี
- อ่านและดีบักง่าย ทดสอบผ่าน Postman ได้ง่ายโดยไม่ต้องพึ่งพาตัวถอดรหัส
- เป็นมาตรฐานหลักของ REST API และ Web Application ทำงานร่วมกับ JavaScript/Node.js
- รองรับ Dynamic Data หรือข้อมูลที่มีโครงสร้างเปลี่ยนแปลงบ่อยได้โดยไม่ต้องแก้หรือคอมไพล์ Schema ใหม่
#### ข้อเสีย
- ต้องส่งชื่อ Key ซ้ำ ๆ ไปในทุกชุดข้อมูล ทำให้สิ้นเปลือง Bandwidth เครือข่าย
- ความเร็วในการประมวลผลช้า การแปลงข้อความเป็น Object (Serialization / Deserialization) กินพลังประมวลผลมากกว่าข้อมูลแบบไบนารี
- ไม่มี Type Safety ขาดการบังคับประเภทข้อมูลที่ มีความเสี่ยงที่ข้อมูลผิดประเภทจะหลุดเข้าไปในระบบ

### Protocol Buffer
#### ข้อดี
- ขนาดไฟล์เล็กและส่งข้อมูลได้รวดเร็ว เข้ารหัสเป็นข้อมูลไบนารีแบบย่อขนาด ตัดชื่อ Key ทิ้ง เหลือเพียง Field Tag ทำให้ใช้ Bandwidth น้อยลงอย่างมาก
- ประสิทธิภาพสูงมาก กระบวนการ Parse ข้อมูลทำได้เร็วและใช้ CPU น้อยกว่า JSON 
- มี Type Safety สำหรับประเภทข้อมูล
- โครงสร้างข้อมูลถูกกำหนดไว้ชัดเจน หากมีการแก้ไขเพิ่มลดฟิลด์ สามารถจัดการเวอร์ชันข้อมูลได้โดยไม่กระทบระบบเดิม
- สามารถคอมไพล์ไฟล์ .proto เดียวกันออกมาเป็น Data Model ให้กับหลายภาษา (Go, Python, Java, C++) ช่วยลดความผิดพลาดในการเขียนโมเดลซ้ำซ้อน
#### ข้อเสีย
- อ่านด้วยตาเปล่าไม่รู้เรื่อง ข้อมูลส่งมาในรูปของ Byte Array หากไม่มีไฟล์ .proto กำกับ จะไม่สามารถรู้ความหมายของข้อมูลได้
- ขั้นตอนการพัฒนาซับซ้อนกว่า ต้องติดตั้งตัวคอมไพล์ (protoc) และต้องสร้างโค้ดใหม่ทุกครั้งที่มีการอัปเดต Schema
- ไม่เหมาะกับ Client-side ทั่วไป การใช้งานบน Browser ฝั่ง Frontend โดยตรงทำได้ค่อนข้างยากและมีเครื่องมือสนับสนุนจำกัดเมื่อเทียบกับ JSON
#### การเลือกใช้งานในเชิงสถาปัตยกรรม
- เลือกใช้ JSON เมื่อพัฒนา API สำหรับภายนอก สื่อสารระหว่าง Frontend กับ Backend หรือระบบที่ต้องการความคล่องตัวในการปรับโครงสร้างข้อมูล
- เลือกใช้ Protobuf เมื่อใช้สื่อสารกันเองภายในระบบหลังบ้าน งานประมวลผลข้อมูลขนาดใหญ่ หรือระบบ IoT และ Mobile App ที่มีข้อจำกัดด้าน Bandwidth และพลังงานเครือข่าย
