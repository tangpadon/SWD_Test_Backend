## Response Section
#### Atomicity (A) การทำงานให้สำเร็จทั้งหมด หรือไม่ทำเลย
ทุกคำสั่งใน Transaction เดียวกันต้องสำเร็จครบทั้งหมด หากมีจุดใดจุดหนึ่งล้มเหลว ระบบจะย้อนค่ากลับทั้งหมดเหมือนไม่เคยมีอะไรเกิดขึ้น
- ฝั่งฐานข้อมูล มีการเก็บ Log เพื่อรองรับการ Rollback
- ฝั่่งแอปพลิเคชัน กำหนดขอบเขต Transaction ว่าคำสั่งไหนบ้างให้เป็น Transaction เดียวกัน

#### Consistency (C) ความสอดคล้องของข้อมูล
ข้อมูลก่อนเริ่มและหลังจบ Transaction จะต้องอยู่ในสถานะที่ถูกต้อง และสัมพันธ์กันเสมอ
ข้อมูลนำเข้า และผลลัพธ์ต้องสอดคล้องกับที่ใส่เข้าไปจริงๆ หากปรับเปลี่ยนข้อมูล ระบบจะต้องสามารถรักษาความถูกต้องของข้อมูลนั้นทั้งหมด
- ฝั่งฐานข้อมูล ตรวจสอบและบังคับใช้กฎพื้นฐานของ Schema เช่น Primary Key, Foreign Key, Unique Constraint, NOT NULL และ Check Constraint
- ฝั่งแอปพลิเคชัน ควบคุมกฎเกณฑ์ที่ฐานข้อมูลไม่สามารถตรวจได้ เช่น การคำนวณส่วนลด การตรวจสอบสถานะบัญชีย้อนหลัง หรือการตรวจสอบเงื่อนไขความถูกต้องก่อนยิงคำสั่งบันทึก

#### Isolation (I) เป็นอิสระต่อกัน
การทำงานของ Transaction หลายรายการที่เกิดขึ้นพร้อมกันจะต้องแยกจากกันเป็นอิสระ ผลลัพธ์ต้องเหมือนการทำงานทีละรายการ โดยแต่ละตัวจะไม่เห็นข้อมูลระหว่างทางที่ยังทำไม่เสร็จ
- ฝั่งฐานข้อมูล จัดการการเข้าถึงข้อมูลพร้อมกัน เช่นการล็อค Row/Table
- ฝั่งแอปพลิเคชัน แอปพลิเคชันต้องจัดการ Deadlock Handling เช่น การเขียนโค้ดดักจับ Exception และสั่ง Retry

#### Durability (D) ความคงทนของข้อมูล
เมื่อ Transaction ยืนยันสำเร็จแล้ว ข้อมูลจะต้องถูกบันทึกอย่างถาวรลงในหน่วยเก็บข้อมูล แม้ไฟดับหรือเซิร์ฟเวอร์ Crash หลังจากนั้น ข้อมูลก็จะไม่สูญหาย
- ฝั่งฐานข้อมูล มีการเก็บ Log เพื่อรองรับการ Rollback เมื่อคำสั่งสะดุด และใช้กู้คืนข้อมูลเมื่อเซิร์ฟเวอร์ดับกะทันหัน
- ฝั่งแอปพลิเคชัน ต้องรอผลยืนยันจากฐานข้อมูลให้เสร็จสมบูรณ์ก่อน จึงจะส่ง Response สำเร็จกลับไปให้ Client เพื่อป้องกันกรณีตอบผู้ใช้ว่าสำเร็จแต่ข้อมูลยังไม่ถูกบันทึก
